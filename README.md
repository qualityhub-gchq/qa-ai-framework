# QA AI Framework

[![Regression](https://github.com/qualityhub-gchq/qa-ai-framework/actions/workflows/regression.yml/badge.svg)](https://github.com/qualityhub-gchq/qa-ai-framework/actions/workflows/regression.yml)

An **AI-assisted test automation framework** built with **Playwright + TypeScript**, using
**Claude Code** and **Playwright Test Agents** to design test cases, generate and maintain
automated tests, and triage failures into **GitHub Issues** — all running in **GitHub Actions**.

> Portfolio project by **Geanina Chavarria** · [LinkedIn](https://linkedin.com/in/geanina-chavarria)

---

## What it does

| Capability          | How                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------- |
| ✍️ Test case design | `playwright-test-planner` agent drafts plans in `specs/`, reviewed by a human QA        |
| 🤖 Test automation  | `playwright-test-generator` agent writes tests, refactored into Page Objects + fixtures |
| 🩹 Test maintenance | `playwright-test-healer` agent repairs broken locators (changes are reviewed)           |
| 🔎 AI Explorer      | Enter a URL in GitHub Actions → plan + tests + results come back as a draft PR          |
| 🔁 Regression       | GitHub Actions: `@smoke` on every PR, full `@regression` nightly                        |
| 🐞 Bug reporting    | AI Bug Reporter reads failed runs and files de-duplicated GitHub Issues                 |
| 📊 Reporting        | Playwright HTML report with traces, screenshots and video on failure                    |

## Architecture

```
 Human QA ──► Planner agent ──► specs/*.md (test cases) ──► human review
                                     │
                                     ▼
              Generator agent ──► tests/*.spec.ts ──► refactor (POM, fixtures, tags)
                                     │
                                git push / PR
                                     ▼
   GitHub Actions: lint + typecheck ──► Playwright (@smoke on PR, @regression nightly)
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
          HTML report + traces             on failure: AI Bug Reporter
             (artifacts)                   ──► GitHub Issue (label: ai-triaged)
```

## 🔎 AI Explorer — URL in, Pull Request out

Run **Actions → AI Explorer → Run workflow**, enter a URL (and optionally a user story).
The workflow then:

1. **Validates** the URL against an allowlist (`config/explorer.json`) — https only, approved practice sites only.
2. **Claude explores** the page in a real browser (Playwright MCP) and writes a **test plan** to `specs/generated/`.
3. **Claude automates** the top scenarios into `tests/generated/` and stabilises them.
4. The **workflow re-runs the tests itself** (the AI doesn't grade its own work), lints and formats them.
5. Opens a **draft Pull Request** with the plan, tests, pass/fail table, report link and a reviewer checklist.

```
URL + requirements ─► allowlist check ─► Claude: explore → plan → automate → stabilise
                                              │
                         workflow: run tests · lint · format · summary
                                              ▼
                         Draft PR (label: ai-generated) ─► human QA review ─► promote to @regression
```

**Guardrails:** manual trigger only · allowlisted domains · no destructive actions · generated tests are
tagged `@generated` and never run in the regression until a human reviews and promotes them · only
`specs/generated/` and `tests/generated/` can be changed by the PR.

**The oracle problem:** AI can observe what a site _does_, not what it _should_ do. Without requirements a
generated test may lock in an existing bug — that's why the requirements input exists and why every
generated PR needs human review. When behaviour contradicts the requirements, the test is marked
`test.fixme` with a `POTENTIAL BUG` note instead of being "fixed" to pass.

**Setup (one time):**

1. Locally run `claude setup-token` and copy the token (uses a Claude Pro/Max subscription).
2. Repo → Settings → Secrets and variables → Actions → New secret `CLAUDE_CODE_OAUTH_TOKEN`.
3. Repo → Settings → Actions → General → Workflow permissions → **Read and write** +
   **Allow GitHub Actions to create and approve pull requests**.

> Note: PRs opened with the default `GITHUB_TOKEN` don't trigger other workflows, so the Regression
> check doesn't start automatically on AI Explorer PRs. Re-run it by pushing a commit to the PR branch.

## Using the AI agents (locally)

```bash
claude      # start Claude Code in the repo root
```

- **Plan:** _"Use the playwright-test-planner agent to create a test plan for the checkout flow. Save it to specs/checkout.md."_
- **Generate:** _"Use the playwright-test-generator agent to automate TC-LOGIN-005 from specs/login.md."_
- **Heal:** _"Use the playwright-test-healer agent to fix the failing tests."_

> Agent definitions should be regenerated after upgrading Playwright: `npx playwright init-agents --loop=claude --project=ui`

## 🧩 Claude Skills (`.claude/skills/`)

Skills are short, versioned **SOPs for the AI**: a `SKILL.md` with the steps for one job, plus reference files Claude loads only when needed.

| Skill                 | Run it with                 | What it does                                                                                                                                             |
| --------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `writing-bug-reports` | `/writing-bug-reports TC-…` | Failing or fixme test → GitHub issue: bug template, severity rules, keyword-based duplicate check. The **AI Bug Reporter workflow uses the same Skill**. |
| `promoting-tests`     | `/promoting-tests TC-…`     | Reviewed generated test → regression: dedupe by equivalence class, Page Objects, next free ID, specs updated, validate-fix-repeat until green.           |

Practices followed: one job per Skill · short `SKILL.md` (under 70 lines) with details in reference files one level deep · clear "what + when" descriptions · house rules stay in `CLAUDE.md` (not copied) · a validation step before "done" · each Skill has an `evals.md` with real cases from this project · changed only through Pull Requests.

## Best practices applied

- **Human-in-the-loop:** AI drafts, a QA engineer reviews every plan, test and bug.
- **Traceability:** every test title starts with a test case ID from `specs/`.
- **Page Object Model + fixtures** — no duplicated setup code.
- **User-facing locators** (`getByRole`, `getByPlaceholder`, `getByTestId`) — no XPath.
- **No hard waits** — enforced by ESLint (`playwright/no-wait-for-timeout`).
- **Independent, parallel tests** with fresh data from builders.
- **Flaky-test awareness:** retries only in CI; tests passing on retry are reported as flaky, not ignored.
- **Secrets** live in `.env` (git-ignored) and GitHub Secrets — never in code.

## Design decisions

- _Why Playwright?_ One tool for UI + API, auto-waiting, built-in tracing, parallelism and AI agents.
- _Why only failures after retries become issues?_ To avoid flooding the backlog with flaky noise.
- _Why the `ai-triaged` label?_ AI classification can be wrong; a human confirms before work starts.
